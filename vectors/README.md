# Golden vectors

Each `*.json` file here is a list of input/output cases that the Rust crate, the Python bindings and the WebAssembly bindings must all reproduce. The format is `golden-vectors@1` from [evidence-kernel](https://github.com/chethandvg/evidence-kernel).

The vectors are generated by [`generate.py`](generate.py), the reference (oracle) implementation. Nothing in it calls the Rust code. It has three parts:

- **`lifesound.py`'s code**, copied from the project's earlier Python toolkit and run with numpy: the instruments as synthesis-theory's oracle copies them (with signal-core's two documented changes: a pure-Python SplitMix64, copied from [signal-core's `vectors/generate.py`](https://github.com/chethandvg/signal-core/blob/v0.1.0/vectors/generate.py) because one repo's Python cannot import another's, in place of numpy's generator, and ln 1000 in `exp_decay`), synthesis-theory's plain-loop reference for `karplus_strong_tuned`, `pan`, `mix_into`, `write_wav`, and `audify` with two changes: audio that would not vary (a constant series, or interpolated samples that are all equal) is an error, and the mean is removed from the samples less the first one (the same in exact arithmetic; `generate.py` asserts that every audify vector agrees with mean removal in Fractions within 1e-15).
- **Exact references for the mapping grammar**: Fractions for the time map, linear maps, octave shifts and folds, heard frequencies and scale quantisation, and mpmath at 50 digits for exponential maps and equal-tempered pitches.
- **Independent Python versions of the crate's new parts**, written from its documentation: `sonify`, `render`, the manifest writer (every manifest is validated against [`../schema/manifest.schema.json`](../schema/manifest.schema.json) with jsonschema, and its SHA-256 computed with Python's `wave` and `hashlib`), the onset detector, the matching of `verify` and its checks of the manifest's description of its events, and `verify_wav` (the WAV file decoded with Python's `wave` and compared byte for byte, and in its peak, with a new render of the manifest's events).

Regenerate with:

```bash
python vectors/generate.py   # needs numpy, mpmath and jsonschema
```

| File | Functions | Tolerance |
|---|---|---|
| [`maps.json`](maps.json) | `to_audio`, `to_real`, `map_value`, `map_pitch`, `quantise`, `heard_hz` | 1e-14 relative (`quantise` exact) |
| [`audify.json`](audify.json) | `audify` | 1e-12 |
| [`events.json`](events.json) | `sonify` | 1e-12 |
| [`render.json`](render.json) | `render` | 1e-12 |
| [`manifests.json`](manifests.json) | `write_manifest` (its manifest; the SHA-256 and every text exact) | 1e-12 |
| [`onsets.json`](onsets.json) | `detect_onsets`, `verify`, `verify_wav` | 1e-12 relative, 1e-9 absolute |
| [`errors.json`](errors.json) | invalid input, in every function (the crate's own input rules, not oracle output) | — |

Tolerances are `max(abs, rel · |expected|)`; strings (the SHA-256s, names, claim ids), booleans and whole numbers must match exactly. Why each is what it is (the largest differences measured with the Python bindings are in brackets):

- **1e-14 relative** for the maps: each is one to three rounded operations (a division and an addition for the time map; a subtraction, division, multiplication and addition for a linear map; a `pow` for an exponential one and for equal temperament), against the exactly rounded value, so a few ulps at most [2.3e-16].
- **1e-12** (`rel = abs = 1e-12`) for `audify`, `sonify`, `render` and `write_manifest`, as in signal-core and synthesis-theory: the crate evaluates the same formulas in the same order as numpy, and the remaining differences come from numpy's own `sin`, `exp` and `pow` and its pairwise sums (the mean removed by `audify`) [audify 3.3e-16, events 1.7e-16 relative, render 5.7e-15, manifests 2.3e-16 relative]. The audify step of one unit in the last place near 7e4 comes out alike in both: once the first sample is subtracted, its samples are whole multiples of that unit, so their sums and mean round alike. The absolute part covers samples near 0.
- **Exact SHA-256s** in `manifests.json`: rendered to 16-bit PCM with dither, the crate's samples and the oracle's agree to the last bit of the WAV file, because a sample would have to land within about 1e-14 of a rounding boundary of the 16-bit grid to change; checked on the platforms CI runs.
- **1e-12 relative, 1e-9 absolute** for `detect_onsets`, `verify` and `verify_wav`: onset times are whole frames divided by the sample rate and match exactly [0], and so do the lists of missing, extra and within-note onsets and every true/false field; the report's recovered real times and errors are differences of nearly equal numbers, so they get an absolute tolerance [1.4e-14].

To keep the files small, every render uses a short signal at a low sample rate (1 to 8 kHz), and `onsets.json` (compact JSON) holds one rendered piece (1.24 s at 1 kHz, rounded to six decimals, which is part of the input, not a tolerance), one WAV file (the same notes 0.2 s into the audio, as a list of its 5,604 bytes), and one chime from a cited source (140 frames and its 604-byte WAV file) with five manifests that misdescribe it. Every case names the claim in [`claims.yaml`](../claims.yaml) that it tests. A JSON `null` is `None` in Rust and Python and `null` in JavaScript. `write_manifest` returns the manifest and the WAV file; the vectors check the manifest, whose SHA-256 covers the file. The round trip on longer renders, at 8 to 48 kHz and with every instrument, is a property test in [`tests/roundtrip.rs`](../tests/roundtrip.rs), not vectors here.
